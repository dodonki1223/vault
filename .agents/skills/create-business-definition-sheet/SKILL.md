# 業務定義シート作成

## 目的

1つの業務について、『業務設計の教科書』WORKING 1 で定義されている業務定義シートを作成する。この skill は 1 業務 = 1 シートの作成だけを担当する。複数業務をまたぐ「業務の地図」の作成、個別工程の詳細なフロー設計は別 skill またはメインのエージェントに任せる。

業務定義シートがそもそも何か、なぜ必要か、目的と OUTPUT の違いなどの背景を確認したい場合は `references/business-definition-sheet-overview.md` を読む。ユーザーから「業務定義シートとは何か」を聞かれた場合もこの参照先を使う。

## 事前確認

ユーザーの依頼文やこれまでの会話で、すでに分かっている項目は再質問しない。

## 情報源の確認

作業前に、業務定義シートの元になる情報源が何かを確認する。

- **対話のみ**: 資料が渡されていない場合、下記の「インタビュー」の通り 1 問ずつ確認して埋める。
- **資料から作成**: ユーザーが貼り付けたテキスト、ローカルファイル、または fetch 系 skill / `workflow-create-business-definition-sheet` から渡された取得済み情報がある場合、その資料をまず読み、9 項目のうち資料から読み取れるものを可能な限り埋める。埋まらない項目、資料の記述だけでは判断できない項目だけを「インタビュー」の手順で 1 問ずつ確認する。すでに埋まっている項目は再確認しない。

この skill 自体は Slack、Notion、Docs、GitHub などの外部システムへ資料を取りに行かない。資料がまだ外部システムにしかない場合は、対応する fetch 系 skill、または `workflow-create-business-definition-sheet` を先に使うようユーザーに伝える。

資料から抽出する際も、資料中の記述が「目的」を書いているのか「OUTPUT」を書いているのかを見極めて仕分ける(下記「目的と OUTPUT を混同しない」を参照)。資料の記述が曖昧でどちらか判断できない場合は、埋めずに質問対象として残す。

## インタビュー

資料から埋まらなかった項目、または資料が渡されていない場合の全項目を、次の順番で 1 つずつ短く確認する。

1. 業務名
2. 担当者・関係者(主担当だけでなく関係者も含める)
3. トリガー(業務が始まるきっかけ。例: 月初、依頼の受領など)
4. 所要時間(処理にかかる平均的な時間)
5. 発生頻度(毎日・週次・月次・その他のいずれか)
6. 目的(何のためにその業務をやっているのか)
7. INPUT(どんな情報や資料をもとに処理を行っているか)
8. DO(どんな処理をしているのか。詳細化はこの段階では行わない)
9. OUTPUT(処理の完了とはどういう状態か、何が成果物か)

### 目的と OUTPUT を混同しない

目的は「なぜその業務をやっているのか」という背景・存在理由であり、業務の上位概念にあたる。OUTPUT は「この業務が終わったとみなせる状態は何か」という完了条件と成果物である。この 2 つを混同すると、業務の質を高めるための改善・自動化・委託の検討がぶれるため、質問時にも両者の違いを一言添えて確認する。

### 埋められない項目の扱い

ユーザー自身で埋められない項目がある場合、推測で埋めない。「不明・要ヒアリング」として残し、後で関係者にヒアリングが必要な項目として作成結果に明記する。

## 保存先の確認

作成前に、シートをどこに保存するか(ファイルパス、または保存先ディレクトリ)を必ずユーザーに確認する。デフォルトの保存先は決めない。ユーザーから指定がない場合は、保存せずファイル内容だけを提示し、保存先が決まってから書き込む。

## 出力フォーマット

図 W1.1 のレイアウトを再現した Markdown で、1 業務 1 ファイルとして作成する。

```markdown
# 業務定義シート: <業務名>

出典: 『業務設計の教科書』WORKING 1

| 担当者・関係者 | トリガー | 所要時間 | 目的 |
|---|---|---|---|
| ・...<br>・... | ... | ... | ... |

発生頻度: 毎日 / 週次 / 月次 / その他( )

| INPUT | DO | OUTPUT |
|---|---|---|
| ・...<br>・... | ・...<br>・... | **完了とみなす状態**<br>...<br><br>**成果物**<br>... |
```

- 担当者・関係者、INPUT、DO は箇条書き(・)で列挙する。
- 発生頻度は該当する 1 つを残し、他は削除するか取り消し線にせず、選ばれたものだけを書く。
- 「不明・要ヒアリング」の項目は、該当セルにそのまま `不明・要ヒアリング` と書く。

## 作成結果の返答

```markdown
## 作成結果

- 業務名:
- 保存先:

## 不明・要ヒアリングの項目

-
```

不明な項目がなければ「不明・要ヒアリングの項目」は「なし」と書く。

## 境界

- この skill は 1 業務 = 1 シートの作成のみを担当する。複数業務をまたぐ「業務の地図」の統合、個別工程の詳細設計は行わない。
- 外部システム(Slack、Notion、Docs、GitHub など)への取得は行わない。ユーザーが直接渡した資料、または fetch 系 skill / `workflow-create-business-definition-sheet` が取得済みの資料だけを情報源として使う。
- 保存先が確認できるまでファイルを書き込まない。
