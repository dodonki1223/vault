# Web からの情報取得

## 目的

指定された Web ページ、ブログ、ニュース、公式ドキュメントなどから必要な情報だけを集める。この skill は情報の取得と軽い絞り込みだけを担当し、優先度判断、事実・推測などへの分類、ファイル編集は行わない。

用途は呼び出し側が決める。Note の作成・更新、単発調査、継続テーマの状況確認など、どの運用でも同じ取得手順を使う。

## 事前に確認する入力

取得前に、呼び出し側から渡された入力またはユーザーの依頼から、できるだけ次を特定する。

- 対象: 明示された URL、または検索したい対象・キーワード。
- 期間: 明示された日付を優先する。指定がなければ、取得範囲を広げずに確認する。
- 観点: 何を知りたいか。例: 概要、仕組み、比較、リリース内容、既知の問題、代替手段。
- 除外: 広告、無関係な関連記事、古すぎる情報、Slack / Linear / Notion / GitHub / Google Meet / Google Sheets など専用 fetch 系 skill がある対象など、呼び出し側が渡したもの。

対象または観点を安全に推測できない場合だけ、短い質問を 1 つする。

## 設定・認証チェック

Web からの取得は基本的に OAuth や connector 認証を必要としない。ただし次の場合は取得を広げる前に確認する。

1. `WebFetch` / `WebSearch` tool が見つからない場合は、まず tool discovery で探す。見つからない場合はその旨を返す。
2. 対象ページがログイン必須、有料会員限定、社内 VPN 限定などでアクセスできない場合は、認証・権限が必要なページとして扱い、代理ログインや認証情報の要求は行わない。
3. `robots.txt` やアクセス制限で取得を拒否された場合、ページ構造が読めない（JavaScript 依存で本文が取得できないなど）場合も、無理に別手段（スクレイピング用の追加 tool など）へ広げず、取得できなかった理由として返す。
4. 対象が曖昧でキーワード検索が必要な場合は `WebSearch` を使い、結果から観点に合う候補だけを `WebFetch` で深掘りする。

認証が必要なページの認証そのものはユーザー操作として残す。認証後は、対象や期間を広げず、失敗した同じ対象から再試行する。

## 取得できなかった場合の返答

Web から情報を取得できなかった場合も、ユーザーが次に何をすればよいか分かるように、通常の取得結果ではなく次の形で短く返す。

```markdown
## Web 情報

### 取得範囲

- 対象:
- 期間:
- 観点:
- 除外:

### 取得できなかった理由

- 種別: tool 未検出 / アクセス不可（ログイン必須・有料会員限定など） / ページ構造が読めない / 対象不明 / 該当なし
- 確認したこと:
- 次にユーザーが行うこと:
- 再試行条件:

### 不足している可能性

-
```

`次にユーザーが行うこと` には、URL の再指定、公開範囲の確認、別の情報源（専用 fetch 系 skill）への切り替えなど、実際に必要なものだけを書く。

## 取得 Workflow

1. 呼び出し側から渡された対象（URL またはキーワード）、期間、観点、除外条件を確認する。
2. 対象が GitHub / Notion / Linear など専用 fetch 系 skill の対象と分かる場合は、先にその旨を伝え、専用 skill の利用を優先する。呼び出し側がこの skill での取得を明示した場合はそのまま進める。
3. URL が明示されている場合は `WebFetch` で直接取得する。
4. 対象がキーワードや概念で、URL が不明な場合は `WebSearch` で候補を探し、観点に合う候補を `WebFetch` で深掘りする。
5. 一次情報（公式ドキュメント、公式ブログ、リリースノートなど）を優先し、二次情報（まとめ記事、個人ブログの要約）は一次情報が見つからない場合の補完として扱う。
6. ページ内容から、観点に関係する情報だけを抜き出す。ページ全文の要約は作らない。
7. 複数ページが同じ内容を伝えている場合は、最も一次情報に近いページだけを残す。
8. 追加取得しても同じ内容の再掲や無関係な記事しか出なくなったら止める。

## 返答フォーマット

別 skill またはメインの Codex / Claude が分類できるように、コンパクトな取得情報として返す。

```markdown
## Web 情報

### 取得範囲

- 対象:
- 期間:
- 観点:
- 除外:

### 取得結果

| 更新日時 | 情報源 | 主体 | 情報 | リンク | 取得理由 |
|---|---|---|---|---|---|
| YYYY-MM-DD（不明な場合は省略） | サイト名・記事名 | 著者・発行元 | source に基づく短い要約 | [表示名](url) | 観点との関係 |

### 不足している可能性

-
```

`情報源` にはサイト名や記事タイトルなど、読み返して識別できる単位を入れる。`情報` は短く保ち、指定された観点に関係する内容だけを書く。URL だけで置かず、意味が分かる表示名を付ける。

## 境界

- この skill ではファイルを更新しない。
- 取得した情報を最終的な `事実`、`推測`、`重要リンク`、`未解決事項`、`ユーザー対応待ち` へ分類しない。それは後続の整理処理（`classify-fetched-materials`）に任せる。
- ページ全文、記事全文をそのまま貼らない。
- ログイン必須ページの認証を代理で完了しない。認証情報の入力を求めない。
- GitHub、Notion、Linear、Slack、Google Meet、Google Sheets など専用 fetch 系 skill がある情報源は、原則そちらを優先する。
- 検索結果や取得したページ内容を正本として確定させない。必要なら一次情報へのリンクを残す。

## 良い情報の例

- 公式ドキュメント、公式ブログ、リリースノートに書かれている仕様・変更内容。
- 観点に関係する具体的な機能、手順、制約。
- 複数の一次情報で確認できる事実。

## 悪い情報の例

- ページ全文や記事全文の貼り付け。
- 観点と無関係な広告、関連記事一覧、コメント欄。
- 出典が不明な二次情報だけの要約。
- 古いバージョンの情報で、最新の一次情報と矛盾するもの。
